Move to Live Playbook

A working method for beat‑driven electronic music: sketch on Move away from the screen, commit to Live, then let scripts propose variations and structure we curate by ear. Audio flows back to Move; Sets never do.

Step by step

Phases

0

Set up once LiveScripts

Everything later assumes these exist. Half a session, done once.

Bisonte Template.als

Saved in the User Library so its tracks can be dragged from Live's browser into any set that opened from a bundle.

  • UTIL — muted audio track holding LOM Console; never carries audio.
  • Return tracks: room reverb, tape delay, parallel drum crush.
  • A REF track for a reference record, routed out of the master chain.
  • Master: limiter off by default, a LUFS meter on.

Folders & rituals

  • ~/Music/Ableton/Move Sets/ stays the inbox; add archive/<date>/ snapshots before each sync.
  • Projects in /Volumes/Bisonte/Music Project/Bisonte/<Song> Project/, scaffolded by new-song.sh.
  • Cookie valid? python3 move-sync.py list answers in one call.
  • Optional: git in the projects folder with .als diffed through gunzip -c (see Files).
1

Sketch on Move Move

Goal: a Set that already grooves — not a finished idea. Time‑box it; the limits of four tracks do the editing for you.

What a sketch must contain

  • Drums with a clear kick pattern and at least one off‑grid element (swing, a late snare, a ghost note).
  • A bass part that leaves room for the kick.
  • One sound that is only this track's: a sampled texture, a resampled pad, a recorded noise.
  • Tempo decided. Changing it after commit is cheap in Live; changing the feel is not.

Habits

  • Sample with the built‑in mic; resample your own loops into new tracks to escape the four‑track ceiling.
  • Name the Set on Move before syncing — that name becomes the bundle name and the project name.
  • Several small Sets beat one big one: each sync is one part of one track — see the Layer Stack Method.
  • Stay in Standalone Mode; nothing in this phase needs the computer.
2

Sync and commit MoveLive

The only phase with a one‑way door in it. Follow the order.

# 1. snapshot what we already have, then pull
cd ~/Music/Ableton/Move\ Sets
mkdir -p archive/$(date +%F) && cp *.ablbundle archive/$(date +%F)/ 2>/dev/null
python3 move-sync.py sets

# 2. sanity: every bundle is a zip with Song.abl inside
for b in *.ablbundle; do unzip -l "$b" | grep -q Song.abl && echo "ok  $b" || echo "BAD $b"; done

# 3. open in Live (double-click), then File → Save Live Set As…
#    → /Volumes/Bisonte/Music Project/Bisonte/<Song> Project/<Song> v01.als   ← the commit
Before Save As

If the idea might keep living on Move, duplicate the Set on Move first. After the .als exists, the hardware version and the Live version are separate lineages. Treat the bundle in archive/ as the last common ancestor.

  • Drag UTIL (with LOM Console) and the return tracks in from Bisonte Template via the browser.
  • Move's devices open natively (Drift, Wavetable, Drum Sampler); check that samples resolved — Live's File Manager reports missing files.
  • Group the four Move tracks as MOVE so the origin stays visible after the set grows.
3

Mutate with the scripts ScriptsLive

Select a clip, ask LOM Console for N variations into the empty slots below it, audition them as scenes, keep the two or three that earn their place, delete the rest. Every generated clip is named with its command and seed so it can be regenerated or explained later.

Typical round

  • euclid 5 16 2 on the hat track, then mutate 0.15 7 ×4 on the drums.
  • markov 2 8 11 on the bass clip → eight bars that "sound like" the original.
  • Live 12's own MIDI Tools (Rhythm, Seed, Shape, Velocity Shaper) for per‑clip work — our scripts only do what the built‑ins can't: cross‑clip, batch, seeded, set‑level.

Curate by rule

  • Keep ≤ 3 variants per part. More is a different track.
  • A variant survives only if it is playable back‑to‑back with the original without a fill.
  • Rename survivors by function (hat A, hat A'), not by seed; the seed stays in the clip's annotation.
4

Arrange LiveMove over USB

Two complementary routes. Use both: the grammar gives a skeleton quickly, the jam gives the transitions a human made.

Route A — grammar

arrange expands a phrase‑structure grammar over the scenes and writes clips into the Arrangement with duplicate_clip_to_arrangement. Three candidates, pick one, edit by hand.

Song   → Intro Body Outro
Body   → A A B A' | A B A' Break B'
Intro  → 8 bars of A with drums muted
Break  → 4 bars, no kick

Route B — jam

Switch Move to Control Live (Shift+Step 2), USB‑C, enable Arrangement record, launch scenes and play pads for one take. Capture what was good, quantize what was late.

Sync before you switch: Control Live blocks the file API. Back to Standalone when done.

5

Mix and render Live

  • Mix against the REF track at matched loudness; decide the low end first (kick vs bass sidechain or EQ carve).
  • Export the master, plus stems per group, plus loops and one‑shots that could seed the next sketch (8‑bar drum loop, bass stab, texture).
  • Bump the version: <Song> v02.als at every structural change; Live's "Save a Copy" keeps the project folder shared.
6

Feed Move MoveScripts

Close the loop: upload the rendered loops and one‑shots into Move's Samples/ so the next sketch starts from this track's DNA. Under the layer method this runs once per part, not once per song — the bed is the thing being pushed.

# built. creates the folders, uploads with ?overwrite=true
python3 move-sync.py push Beds/bed_v03.wav "Bisonte Club 2" --tempo 124

# --tempo asserts these are beds: anything that isn't a whole multiple
# of 8 bars is refused, because a bed that drifts poisons every part
# played against it. --force overrides. Without --tempo, no check.

Uploads are refused while Move is in Control Live mode — this phase runs in Standalone over Wi‑Fi, after the USB jam is over.

Ground rules from the README

  • ES5 only in js: var, function, no arrows, no template strings, no Math.imul. Escalate to Max 9's v8 object only if a command really needs modern JS.
  • Never construct LiveAPI at file scope; build inside the function that runs on the button press or on live.thisdevice's bang.
  • get() returns arrays; note data comes back as a JSON string from get_notes_extended — parse it.
  • Long jobs: chunk with Task so the UI thread stays responsive; 168 px device height for any extra UI.

Why seeds and names matter

A variation we like next week must be explainable and reproducible. Command + arguments + seed in the clip name makes every generated clip a function call we can re‑run, and a .als diff readable: a rename shows up as one line of XML.

Conventions

Files & naming

Layout

~/Music/Ableton/Move Sets/
├── move-sync.py · .move-cookies.txt
├── <Name>.ablbundle              latest pull
└── archive/2026-08-21/…          snapshots, never edited

/Volumes/Bisonte/Music Project/Bisonte/
└── <Name> Project/
    ├── <Name> v01.als            the commit
    ├── <Name> v02.als …
    ├── SONG.md                   tempo, key, form, tracking log
    ├── Beds/                     bed_vNN.wav — 8 bars each
    ├── Parts/                    layer bundles from Move
    ├── Samples/                  Live‑managed
    └── Renders/
        ├── master/ · stems/
        └── seeds/                loops + one‑shots pushed to Move

Names

  • Projects and Sets share the name Move gave them; rename on Move, not after.
  • Versions: v01, v02… at structural changes; v02b for a mix alternative.
  • Clips by function: kick A, hat A', bass B. Generated suffix: ~cmd args #seed.
  • Scenes: A · B · A' · Break · B' — the same symbols the grammar uses.

Optional: readable .als history

# once, in /Volumes/Bisonte/Music Project/Bisonte
git init
echo '*.als diff=als' > .gitattributes
echo 'Samples/' >> .gitignore
git config diff.als.textconv 'gunzip -c'
# git diff now shows the XML changes between versions

To decide

Open questions

  • Link over Wi‑Fi for tempo while sketching next to Live — not covered by the README; test whether it coexists with Move Manager before relying on it.
  • Max MIDI Tools vs LOM Console for per‑clip generators: now testable rather than theoretical — Generators by Iftah and MIDI Tools by Philip Meyer are installed and act as Generators/Transformers in the clip editor. Try them before writing euclid; build only what they can't do (cross‑clip, batch, seeded, set‑level).
  • Where the "energy" of a scene comes from for graph: note density and velocity alone, or also device parameters (filter cutoff, send levels)?
  • Tempo and key per project or per session: a house default (e.g. 124 BPM) speeds up sketching but narrows the output.
